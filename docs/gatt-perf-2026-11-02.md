# N32WB452 GATT 性能测试与优化

测试日期：2026-11-02。Mac 原生 CoreBluetooth 作为 central，N32WB452 分别运行板载 NimBLE host 和 USB bridge + macOS blectl host；相同板子、相同 Mac、同一物理摆放，方向 up 为 Mac → server，down 为 server → Mac。

## 方法与边界

参考 `/Volumes/aigo_1t/GitRepo/wch-trouble-workspace/ch32v208-nimble/docs/l2cap-gatt-perf-2026-10-31.md` 与其 macOS `perf.py` 的口径：独立连接，持续积压的单向 write-without-response / notification，序号及 pattern 校验、结束后字节数核对、尾部排空计入耗时；测量时不连接调试探针。失败立即停止，保留原始日志；单独连接 RTT 的诊断不计入性能数据。

本仓库的独立工具位于 `tools/macos-gatt-perf/`，不修改软链接指向的参考工程。正式 runner 每轮交错 up/down，各 3 次 × 30 秒；记录本地 ELF/工具源码/服务源码快照和哈希。`payload_kbps = 接收端校验应用字节 × 8 / 测量秒数 / 1000`，包含 4 字节序号，排除协议头及配置操作。上传用 server 接收到最后字节的计时，下载用 Mac START 写确认（若首包更早则取首包）到最后校验包的计时。v5 stats 上传使用 MCU TIM2 1 MHz / desktop monotonic 微秒时钟。

参考标准的无线前提（PHY 命令成功、有效 DLE TX/RX=251、244 字节负载）需要单独核对。NZ8801 的 LE PHY 命令返回 Unknown Command；`--legacy-controller` 只允许已知 LE 默认 1M 降级，明确记录，不能视为参考标准的 PHY PASS。DLE 未观测时为 unknown；控制器硬件错误计数不可获取，零填充字段不能作为无无线错误的证据。

服务新增特征时，macOS 缓存旧 GATT 数据库。原地址 `1E:AB:26:68:84:66` 仍仅发现旧 5 个特征，故本轮 schema identity 升级为 nimble `…:67`、bridge perf-server `…:68`，用于强制新服务发现。广播分别为 `N32-NimBLE` / `N32-Bridge-Perf`。

nimble 下行另一次 RTT 诊断证实 `TX ACL ready timeout; frame not sent`，并随后出现 `no evt buf, drop code=0x13`（Number Of Completed Packets）。无探针的测量也同样复现 sequence 8→9，故不是探针才产生的现象。该问题需要修复 transport/流控，不能用忽略序号错误的方式增加表面吞吐。

RTT 观察 ATT 交换为 host `02 f7 00`、Mac 回复 `03 b9 00`，实际 ATT MTU=185；早期 summary 在断开后读取 CoreBluetooth 的 `maximumWriteValueLength(.withoutResponse)` 得到默认 20，该值不能代表传输中的上限；工具现已改为连接中配置阶段捕获。真实 MTU=185，允许 182 字节应用负载，244 字节请求正确拒绝。此时 CI=15ms，有效 DLE 未收到变更事件，不能声称 DLE251。v5 微秒计时 5.116784s 与 Mac 5.133s（含尾部）吻合；下行生产 4.996117s 与请求的 5s 吻合。

## 已实现的修复与优化

1. 板载 NimBLE host 的原调用实际创建 priority 1 任务，和注释中的 priority 4 不一致；RX priority 3 会在 SPI TX 时抢占并清 wakeup。现在显式创建 priority 4、4 KiB stack 的 host 任务。
2. SPI ready 等待允许 RX 继续排空；进入片选事务前再检查，并只在实际 CS 低电平事务内暂停任务切换，避免 RX/TX 对同一 SPI/握手交叉操作。等待阶段不暂停调度，USB 中断仍可处理。
3. MCU 和 blectl 的 NPL 日志增加 WARN 门槛，消除性能流量中的逐包 DEBUG/INFO/hex printf，保留 WARN/ERROR 和应用状态记录。基线 blectl 的大量 packet logging 与 ACL pool 丢包同时出现；组合修复后消失，未逐项隔离日志过滤的独立收益。
4. 新增显式 DLE 请求步骤（control opcode 3），先请求 251 octets / 2120 µs，等待独立过程后再请求 CI；收到真实 LE Data Length Change event 后才报告有效 DLE251。不能仅凭请求返回 rc=0 判定协商成功。
5. 共用同一份 GATT 服务和序号/pattern 协议；v5 统计提供真实 ATT MTU、CI、DLE 和微秒计时。客户端在连接中的配置阶段缓存最大 write-without-response 长度，避免断开后读到默认 20。

修复后先做两种模式的 20B 双向 5 秒 smoke：nimble up/down=75.80/19.02 kbps，bridge=75.39/18.85 kbps，均完整无错；首次下行丢 sequence 8 的问题不再复现。随后明确请求 DLE251，使用本 Mac ATT MTU185 能承载的 182B 负载开始正式重复测试。

## 与参考标准的对应及剩余限制

- 单向持续负载、独立连接、前后状态读取、接收端逐字节校验、尾部排空和硬件计时均对齐；每方向 3×30 秒，强于参考报告的 2×15 秒时长。
- 实际 DLE251、CI15ms 已核对。PHY 命令不支持，明确记录默认 LE 1M 降级，不能伪称通过 PHY 命令确认；本 Mac ATT MTU185，因此负载182B，不能与参考244B结果直接视为完全同条件。报告 `reference_standard_met=false` 与应用数据完整性通过是两个不同结论。
- 两种模式上行约223～229kbps，下行约78～79kbps；换到桌面 host 后下行没有明显提升。这说明仅更换 host 并未解除当前下行限制，但还不能据此确定是控制器连接事件调度还是共享 SPI 通路。测试结束后单独读取板载 NimBLE 的 HCI ACL buffer size 为251，排除了主机按27B HCI buffer分片的猜测（`nimble-post-test-hci-buffer-size.log`）；这次诊断不计入吞吐测量。
- 保留 SDK 原有 SPI 帧后1000us间隔。未用未经验证的时序缩短换取表面吞吐，也不声称当前结果是NZ8801射频极限。未测2M/Coded、长距离或长时稳定性。
- 软件验证：两种 MCU 固件及原生 blectl 构建成功，CTest 6/6、macOS客户端自检通过。原生测试覆盖共享service的非法控制、数据损坏、状态切换、32位微秒回绕、DLE请求及协议；runner离线测试覆盖错误/缺包、时间不足、缺少背压、PHY降级、DLE失败和非法参数。


测试后已恢复 **bridge 固件、小核 HCI 状态2**，`blectl info` 自动 JSON 下载后返回 `host synced: yes`。未留下性能服务进程。原始证据另备份至仓库本地忽略目录 `tools/macos-gatt-perf/.build/evidence-20261102/`，不将 ELF/原始大日志纳入 Git。
